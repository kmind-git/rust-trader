# FIX 回报直达发送端与持久输入缓冲

2026-09-15 已实施。此改动延续现有线程模型，消除回报对接收线程网络读取的等待；没有引入 EngineHost、异步运行时或新的投递线程。

## 回报路径

```text
任一会话 reader → Engine Mutex → 撮合 / Report
                                    ↓ 非阻塞 try_send
                         目标会话唯一有界出站队列
                                    ↓ 唤醒
                             目标会话 writer → TCP
```

原先的 `Report` 队列和 reader 转发循环已移除。核心通过 `ReportSink` 接口投递领域回报，FIX 层的适配器将回报送入已有 `OutMsg` 队列。公共 `Engine::register_session` 仍兼容原来的 `Sender<Report>` 调用方式。

投递发生在 Engine 的串行操作内，保持不同交易操作产生的回报入队次序。投递只尝试入队，不等待容量，也不在撮合路径执行网络读写或 FIX 编码。writer 独占发送序号并完成关联 ID 转换、编码、日志与网络发送。writer 不获取 Engine 锁，不增加相反的锁获取顺序。

每连接仍有 reader 和 writer 两条工作线程。管理消息和交易回报共用一个容量为 1024 条的出站队列；此前是两个各 1024 条的队列。容量为项目内部常量，不是 QuickFIX 配置项。队列仍使用标准库的有界通道，不能据此称为无锁或 wait-free。

## 握手、退出与故障

Logon 应答及品种初始化消息先入队，再向 Engine 注册回报目标，因此业务回报不会超越 Logon 应答。writer 继续统一处理普通消息、ExecutionReport 和 GapFill 的发送序号。

acceptor 退出时，在 Engine 锁内移除会话并清理订单，然后将最终 Logout 排入同一队列。先前已入队的回报在 Logout 前发送；清理完成后不会再产生指向该会话的回报。writer 写出最终 Logout 后立即退出，不再发送心跳或后续消息。initiator 主动发起 Logout 时仍按原流程等待对端应答。

队列满或消费者退出仍采用原有失败后断连策略。改动减少等待和积压环节，但没有增加成交回报持久化、确认或重放能力；满载/断线时仍不能保证已成交回报全部交付。一个目标失败不会阻塞另一成交方的报告入队，也不会回滚已经成交的交易。慢 socket 写入、同步日志、线程调度及队列积压仍可能导致延迟。

## 输入缓冲

acceptor 与 initiator 每个连接从开始读取时就持有一个 `FrameReader<BufReader<TcpStream>>`。缓冲跨越握手与后续报文生命周期，避免丢弃 Logon 后已预读的订单。头部逐字节解析主要消费内存缓冲，同时去掉定位头部边界的临时 Vec 分配。

acceptor 完成握手后，直接在实际 reader 句柄上设置 500 ms 运行期读取超时；initiator 也显式设置其实际 reader 句柄。该超时用于读循环、心跳和故障检查，成交回报发送不再依赖它。保留原始字节校验、报文与头部长度限制，以及部分报文跨读取超时后继续解析的行为。

## 验证与范围

Rust 回归覆盖输入跨超时续读、粘包、长度/校验和、底层模拟 Read 调用合并、一个出站目标满载不阻塞另一方，以及最终 Logout 后不发送已排队消息。模拟 Read 计数不等于操作系统 syscall 测量。

`tests/fix_delivery.py` 使用独立 FIX42 字典校验器和真实 loopback TCP，验证双方 Logon 与首单一次发送、空闲 MAKER 的五轮成交回报、双方数量和价格、连续序号、唯一 ExecID，以及 Logout 后连接关闭。脚本的 2 秒接收期限用于捕获旧路径的长等待，不是生产延迟承诺。

构建、运行方法见 [测试说明](../tests/README.md)，本地诊断结果与限制见 [性能记录](performance.md)。完整架构方案中的 DAY 扫描、统一时钟、EngineHost、FIX 状态机拆分及可靠恢复能力仍未在此阶段实现。
